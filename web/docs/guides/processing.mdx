# Processing

How the processing works? This chapter explains it in detail.

## Definitions

* **Flow plan**
  A *flow plan* is a definition of one source of information and one destination
  bookkeeping, where the information needs to be stored.
* **Batch** Each completed cycle of fetching information from the source and then
  successfully processing it and delivering the result, is called a *batch*.
* **Run** Once a flow plan is configured, one can *execute* it using
  a run button in the app. New batch is created and as many steps as possible are
  executed. That is a single *run*. The run can result either *completion*,
  *waiting* or *failure*. Failures can be possibly fixed by chaging settings for
  the flow plan and *retrying* by executing another run. Waiting means that the batch
  needs some additional information before it can continue. Once provided, another
  run can be executed.

## Steps of a Batch

A single run executes as many steps as possible.

### 1. Data Fetching

As a first thing that happens, the original data is fetched. Typically it is downloaded
from some specific URL but also can be uploaded manually as a statement file or similar.

Fetching step also knows the latest timestamp, when the fetch has been done before. It
tries to skip older data than the latest known timestamp. It depends on the data source how
accurate this is. However, every data source rather re-retrieves the same entries than
risks the loss of data around the latest timestamp and rather takes care of duplicates
at the later stage.

### 2. Data Parsing

Each data source has their own format. It could be some API data or CSV file for example. However,
before we start our own processing, everything is converted to the JSON-format presenting
the original data. In a simple case, it could be just CSV file converted to the key-value
pairs according to the known column names.

Data is splitted to items presenting either one full transaction or a part of the transaction.
More about partial items [here](/docs/guides/unified-format#multipart-).

### 3. Unifying Items

The trickiest part comes next. We need to understand the original data and convert it
to the intermediate format, that can express everything we are interested in from the
bookkeeping point of view. For that purpose we have developed *[unified format](/docs/guides/unified-format)* to describe
transactions.

Transformation happens using custom *[rules](/docs/guides/rules)*. Well known data source
like a stock broker can have complete rule set to handle entire statement. However,
in general purpose bank statement you need to cook your own recipies to convert the data
to the unified format.

<figure>
<figcaption>**Example**: *Nordnet withdrawal in unified format*</figcaption>
```json
{
  "type":"withdrawal",
  "value":1930,
  "service":"Nordnet",
  "valueAsset":"EUR"
}
```
</figure>

### 4. Analysis

Analysis is a step where all unified items are processed once in their chronological
order. Any change in a balance of any account is tracked. Also the buying prices of
various assets are kept alongside of their respective accounts. Fees are separated from
transactions and recorded to their own accounts. When selling something the difference
between buying and selling price is recorded either as a profit or a loss. Some accounts can
be configured to allow going to negative balance and using different debt account to denote
borrowed money instead. Typically this is used when stock broker let you use margin, i.e.
loan money to you.

This step produces *[generic transactions](/docs/guides/generic-transactions)* that
resembles normal bookkeeping transactions,
but actual information of accounts is still missing. Text symbols are used instead
to represent destination accounts.

<figure>
<figcaption>**Example**: *Withdrawal as a generic transaction*</figcaption>
```json
{
  "time": "2000-05-09T12:00:00.000Z",
  "lines": [
    {
      "text": "Withdrawal from Nordnet-service",
      "amount": "-1930",
      "extras": {},
      "account": "CURRENCY_EUR"
    },
    {
      "text": "Withdrawal from Nordnet-service",
      "amount": "1930",
      "extras": {},
      "account": "EXTERNAL_NORDNET_EUR"
    }
  ]
}
```
</figure>

### 5. Output

Final step is to copy the transactions across to the actual bookkeeping system. This is mostly
a matter of configuring actual accounts to match the generic account symbols produced by
the analysis. Most bookkeeping systems are updated using their API to push changes through
automatically.
