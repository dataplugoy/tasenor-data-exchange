# Processing

How the processing works? This chapter explains it in detail.

## Definitions

* **Flow plan**
  A *flow plan* is a definition of one source of information and one destination
  bookkeeping, where the information needs to be stored.
* **Batch** Each completed cycle of fetching information from the source and then
  successfully processing it and delivering the result, is called a *batch*.
* **Run** Once a flow plan is configured, one can go to the *Executions* and
  press a run button. New batch is created and as many steps as possible are
  executed. That is a single *run*. The run can result either *completion*,
  *waiting* or *failure*. Failures can be possibly fixed by chaging settings for
  the flow plan. Waiting means that the batch needs some additional information before
  it can continue.

## Steps of a Batch

### 1. Data Fetching

As a first thing that happens, the original data is fetched. Typically it is downloaded
from some specific URL but also can be uploaded manualli as a statement file or similar.

Fetching step also knows the latest timestamp, when the fetch has been done before. It
tries to skip older data than the latest timestmap. It depends on the data source how
accurate this is. However, every data source rather re-retrieves the same entries than
risks the loss of data around the latest timestamp.

### 3. Unifying Items

The trickiest part comes next. We need to understand the original data and convert it
to the intermediate format, that can express everything we are interested in from the
bookkeeping point of view. For that purpose we have developed *unified format* to describe
transactions.

Transformation happens using custom *rules*. Well known data source like a stock broker
can have complete rule set to handle entire statement. However, in general purpose bank
statement you need to cook your own recipies to convert the data to the unified format.

<figure>
```json
{
  "type":"withdrawal",
  "value":1930,
  "service":"Nordnet",
  "valueAsset":"EUR"
}
```
<figcaption>**Example**: *Nordnet Withdrawal in Unified Format*</figcaption>
</figure>

### 4. Analysis

Analysis is a step where all unified items are processed once in their chronological
order. Any change in a balance of any account are tracked. Also the buying prices of
various assets are kept alongside of their respective accouts. Fees are separated from
transactions and recorded to their own accounts. When selling something the difference
between buying and selling price is recorded as a profit or a loss. Some accounts can
be configured to allow going negative and using different debt account to denote
borrowed money. Typically this is used when stock broker let you use margin, i.e.
loan money to you.

This step produces *generic transactions* that resembles normal bookkeeping transactions,
but actual information of accounts are still missing. Text symbols are used instead.

<figure>
```json
{
  "time": "2000-05-09T12:00:00.000Z",
  "lines": [
    {
      "text": "Withdrawal from Nordnet-service",
      "amount": "-1930",
      "extras": {},
      "account": "CURRENCY_EUR"
    },
    {
      "text": "Withdrawal from Nordnet-service",
      "amount": "1930",
      "extras": {},
      "account": "EXTERNAL_NORDNET_EUR"
    }
  ]
}
```
<figcaption>**Example**: *Withdrawal as a Generic Transaction*</figcaption>
</figure>

### 5. Output

Final step is to map the transactions to the actual bookkeeping system. This is mostly
matter of configuring actual accounts to match the generic account symbols produced by
the analysis. Most bookkeeping systems are updated using API to push changes through
automatically.
